# MealCountのバックエンド設計

## 要件

### 目的
- obsidianで使っている上記のテンプレートをアプリで自動集計、保存できるようにする

### 設計
- データとして持つもの
  1. 一度の買い物を記録する(purchase)
    - 購入日
   [入力値]
    - 買い物合計金額
    1. 即日消費
    2. 計画消費
    3. 各月消費
    - 仕入れ食数

   [算出値]
    - 実質食費合計 = (即日消費 + 計画消費)
    - その買い物の１食単価 = (実質食費合計 / 仕入れ食数)
  2.冷蔵庫内の食数(MealStock)
    - 現在の冷蔵庫内の食数
    - 自分で修正した１日の消費食数
    - １日の消費食数[デフォルトで1日3食]

  1. 10日ごとに集計する(カレンダーに基づいて、10日後に自動集計して、サマリにまとめる)
  [算出値]
  (10日間の消費食数[30食]を固定値とする)
   - 10日間の食費合計（買い物合計）
   - 10日間の実質食費合計
   - 買い物回数
   - 仕入れ食数
   - 現在の在庫食数 = (前回までの在庫食数 + 仕入れ食数 - 消費食数)
   - 在庫残存日数 = 現在在庫 ÷ 3
     在庫消費予定日 = 現在日 + 在庫残存日数
     -> 何日後に在庫が消費され0になる

  1. 分析（2に基づいて出力される判断指標）
   [算出値]
   (１日3食を固定値とする)
   - 10日間の1食単価 = (10日間の実質食費合計 / 10日間の食数[1日3食 * 10日 = 30食])
   - これから必要な食数 = { (1ヶ月の日数 - 現在の日数) * 1日の食数(3食) }
   - 実質必要な食数 = (これから必要な食数 - 現在の在庫食数)
   - これから必要な食費の合計 = (10日間の１食単価 * 実質必要な食数)

### Resource
  - Resource1. Purchase
    ```
    ※例
    Purchase No.1
    購入日: 2026-09-20
    合計金額: 8,000円
    即日消費: 2,000円
    計画消費: 5,000円
    各月消費: 1,000円
    仕入れ食数: 20食
    ```
    ```
    作成：買い物を記録する
    取得：買い物履歴を見る
    詳細：1回の買い物を見る
    更新：入力ミスなどを修正する
    削除：誤った買い物記録を削除する
            ↓
    POST   /purchases
    GET    /purchases
    GET    /purchases/:id
    PATCH  /purchases/:id
    DELETE /purchases/:id
    ```
  - Resource2. MealStock
    ```
    取得: 現在の在庫食数を見る
    更新: デフォルトの１日の食数を修正する
    ↓
    GET   /meal-stock
    PATCH   /meal-stock/:id
    ```
  - Resource3. Summary(read)
    - 集計結果のためのモデル
    - 第1期間：9/1  〜 9/10
      第2期間：9/11 〜 9/20
      第3期間：9/21 〜 9/30（または月末）


  - Resource4. Analysis(read)
    - 判断指標のためのモデル



### メモ
1. バックエンド設計において、「計算できるもの」と「入力するもの」を分けて考える
2. ドメイン(domain) = アプリにおける固有の概念のこと
    → MealCountにおいて買い物をして、分類、食数に変換、在庫集計、金額集計、これらそれぞれを
    購入（Purchase）
    在庫（Inventory）
    集計（Summary
    として、モデルしたもののことをドメインモデルと言う
3. Resourceとは、API設計においては、取得・作成・更新などの対象として扱うもの
   1. Purchase(購入日、合計金額、実質合計金額...これらを登録、修正、削除する)
   2. summary
   3. analysis
