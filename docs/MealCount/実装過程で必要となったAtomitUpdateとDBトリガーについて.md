# AtomicUpdateについて

## 概要
処理のために、DBにある現在のデータをもとに計算し、更新を一つの操作として行う方法をAtomicUpdateという。
Serviceなどで、DBにあるデータを読み込んで行う処理では、

```text
service → repository → DB
取得
計算
更新
これらが別々で行われ、LostUpdateが発生する可能性がある。
```
この場合、serviceで古いデータを取得し、計算、更新を行うと、期待値通りにならない可能性がある。

## AtomicUpdateの利点
AtomicUpdateを用いることで、DBにある現在のデータをもとに計算、更新を一つの操作として行うため、古いデータによる計算や更新によるLost Updateを防ぐことができる。
特に、購入情報の更新や在庫数の管理など、複数の操作が同時に行われる可能性がある場合に有効である。

「原子」 = atomic（原子性を持つ）操作のことを指す。DB内での一連の処理が全て完了するか、全く行われないかのどちらかであることを意味する。


## トランザクションの利用
購入の保存が成功しても、在庫の更新が失敗するケースでは、データの整合性が崩れてしまう。
そのため、購入と在庫の更新を一つのトランザクションとして扱うことで、どちらかが失敗した場合には全体をロールバックし、処理を差し戻すことで整合性を保つことができる。

## mealCountにおける採用
- `purchase`では、購入情報の作成に伴う在庫数の変更を一つのトランザクションとして、扱い、D1のbatch()で`mealStock`のAtomic Updateを実行している。
- 更新や削除に伴う在庫数の変更も同様に、Atomic Updateとして扱い、さらにDBトリガーを用いることで、`mealStock`を同じトランザクション内で更新処理を行うことができる。
- 同一の`purchase`の競合更新が起きても、version管理による競合検知により、適切に処理が行われる。
- `mealStock`の更新もAtomic Updateとして扱われるため、複数の更新が同時に行われても、Lost Updateを防ぐことができる。

これにより、同一のユーザーが複数の購入情報を更新したりしても在庫数の整合性が保たれ、Lost Updateの発生を防ぐことができる。
