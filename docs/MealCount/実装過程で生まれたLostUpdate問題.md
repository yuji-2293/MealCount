# LostUpdateとは
## 概要
LostUpdateとは、複数のトランザクションが同じデータを同時に更新するとき、後から更新したデータが前の更新を上書きしてしまい、前の更新内容が失われる現象のこと。
この時、データが消失する条件として、「どのタイミングのデータを取得したか」と「どのタイミングで更新したか」が重なる場合に発生する。
古いデータを基に更新を行った場合に、他のトランザクションによる更新が上書きされてしまうことがある。
- 操作の流れ
  - 操作Aがデータを登録
  - この時点で操作Bが変更しようとしている古いデータを取得している
  - 操作Bが同じデータを更新しようとした時、「操作Aの登録前のデータ」を取得してしまっている状態で保存すると操作Aの内容が上書きされてしまう

## mealCountの例
1.ユーザーがスマホを使って購入情報を更新しようとする。
2. 同じユーザーがPCから同じ購入情報を更新しようとする。
3. 先にスマホから更新した内容がデータベースに反映される。
4. PCからの更新がデータベースに反映される。
5. このとき、スマホからの更新内容がPCからの更新によって上書きされ、失われてしまう。

## 対策
1.悲観的ロック
  - データを読み込んだ時点で、他の人にその行を更新させないようにロックをかける方法。
  - ただし、ロックをかけることで他のトランザクションが待たされるため、パフォーマンスに影響を与える可能性がある。
2. 楽観的ロック
  - データを更新する際に、他の人が同じデータを更新していないかを確認する方法。
  - 具体的には、データにバージョン番号を持たせ、更新時にバージョン番号が一致するかをチェックする。
  - バージョン番号が一致しない場合は、更新を拒否し、ユーザーに再度データを取得して更新させる。

### まとめ
LostUpdateは、同時に更新処理が走ることによって発生する問題である。
トランザクションの分離やバッチ処理、ロック方式を行うことで対策できる場合もある。
具体的には、悲観的ロックや楽観的ロックを用いることで、同時更新によるデータの上書きを防ぐことができる。

### 採用
mealCountのプロジェクトでは、他のユーザーを大量に入れることは現時点で想定しておらず、
また、同じ理由からデータの競合が起きることも稀であると考える。
よって、ユーザーが異なる端末による古いデータでの同時更新を防ぐことを考慮する。
そのため、楽観的ロックを採用することとする。
具体的には、データにversion番号を持たせ、更新時にversion番号が一致するかをチェックすることで、同時更新によるデータの上書きを防ぐ。

### 採用理由
mealCountでは、購入と同時に在庫データが更新される。
`purchase`による購入食数の増減の更新は、`mealStock`の在庫数の更新と密接に関連している。
古いデータを基に更新を行うと、`purchase`と`mealStock`の整合性が崩れる可能性を考える必要がある。
そこで、フロントからのリクエストに含まれるversion番号が、DBに保存されているversion番号と一致するかどうかを検証し、
取得時点から、他の操作によって更新されていないことを確認する必要がある。
これには、楽観的ロックを用いて、更新時に最新のデータであることを確認する方法が適している。

### 別の対策
mealCountでは、楽観的ロックとは異なり、AtomicUpdateを用いて、データの更新を原子操作として行うことで、同時更新による競合を防いでいる事案も存在する。
`AtomicUpdate`は、楽観的ロックのように最新のデータであるでとを検証した上で更新を行う種類のものでなく、DBにある現在地のデータをもとに計算し、更新を一つの操作として行う方法である。
この時、serviceで値を計算したり、古いデータを読み込んで更新を行うでなく、DBにある処理の対象となるカラムに対して直接更新を行うことで、原子操作としての更新を実現することでpurchaseのCREATEにおけるLostUpdateを防いでいる。
