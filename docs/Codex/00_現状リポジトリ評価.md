# MealCount: 現状リポジトリ評価

## 結論

MealCountは、購入記録と在庫を題材に、**CRUDから同時更新の整合性へ進むための良い学習用バックエンド**になっている。

特に、次の仕組みが既にリポジトリに存在する。

- `purchases`、`meal_stock`、`users` の3テーブル
- HonoのRoute、Service、Repositoryの分割
- ZodによるHTTP入力検証
- Drizzle / Cloudflare D1による永続化
- 購入作成時の在庫への原子的加算
- `purchases.version` を使う楽観的ロックの試行
- 購入食数変更時に在庫を追随させるSQLiteトリガー

一方、これらはまだ一貫して完成している状態ではない。特に削除、在庫補正、HTTPエラー設計、テストに課題が残る。したがって、現時点は「同時更新を学ぶための実装」として高く評価できるが、ポートフォリオの完成版としては、下記の整合性を検証・統一する段階にある。

## 構成

```text
apps/web
  React + TanStack Query + Hono RPC client
          │ HTTP
          ▼
apps/api
  Hono Route → Service → Repository → Drizzle / D1
                                  │
                                  ▼
                   purchases / meal_stock / users
```

主要な実装は以下にある。

| 関心 | 実装箇所 |
| --- | --- |
| Purchase HTTP API | `apps/api/src/modules/purchases/routes/purchaseRoutes.ts` |
| Purchase業務処理 | `apps/api/src/modules/purchases/services/purchaseService.ts` |
| Purchase SQL組み立て | `apps/api/src/modules/purchases/repositories/purchaseRepository.ts` |
| MealStock SQL組み立て | `apps/api/src/modules/meal-stock/repositories/mealStockRepository.ts` |
| DB schema | `apps/api/src/db/schema.ts` |
| 購入食数更新トリガー | `apps/api/drizzle/0010_UpdateTrriger_Re.sql` |

## 良い点

### DBに守らせるべき制約がある

`apps/api/src/db/schema.ts`には、アプリだけに依存しない制約が定義されている。

```ts
check('meal_count_positive_check', sql`${table.purchased_meal_count} > 0`),
check('current_meal_stock_nonnegative', sql`${table.current_meal_stock} >= 0`),
```

さらに、`meal_stock.user_id`の一意制約と、`purchases.user_id`および`meal_stock.user_id`の外部キーにより、1ユーザーにつき在庫が1件であるというモデルをDBで表現している。

### 作成時の在庫加算は原子的である

`mealStockRepository.buildAddPurchaseMealCountQuery`は、JavaScriptで取得した在庫値を保存し直していない。`meal_stock.current_meal_stock`をSQL式の中で読むため、同時に購入作成が起きても各更新はDBの直近値を基準にする。

### 楽観的ロックを理解するための材料がある

`purchases`に`version`カラムを追加し、更新条件に`id`と`version`を両方指定している。

```ts
.where(and(eq(purchases.id, id), eq(purchases.version, expectedVersion)))
```

これは「画面が読み込んだ版とDBの版が一致する場合だけ更新する」という、楽観的ロックの中心となる考え方である。

### DBトリガーで関連データの不変条件を守ろうとしている

購入食数が更新されたとき、トリガーが在庫を差分更新する。Serviceが更新し忘れても、直接SQLが実行されても、DB更新に追随させる方向性は適切である。

## 現在の重要な課題

### 1. APIの型チェックが失敗する

`pnpm typecheck:api`を実行すると、`purchaseService.deletePurchase`が呼んでいる`mealStockRepository.buildUpdateQuery`が存在しないため失敗する。

```text
Property 'buildUpdateQuery' does not exist on type 'mealStockRepository'
```

削除経路は現状ではビルド可能な状態ではない。これはドキュメントではなく実装上の事実であり、削除処理の動作確認より先に解消すべき状態である。

### 2. 同時更新対策の適用範囲が不統一

購入作成はSQL式による原子的更新を使う一方、削除処理はServiceで在庫を計算した後、絶対値として保存しようとしている。

```ts
const { estimatedStock } = calculateEstimatedStock(...);
const estimatedAfterMealStock = Math.max(0, estimatedStock - mealCount);
```

この間に別リクエストが在庫を変更すると、後から実行された絶対値更新が別リクエストの結果を上書きする可能性がある。これはLost Updateである。

### 3. 楽観的ロックはAPI全体に接続されていない

更新schemaでは`version`が必須である。

```ts
export const updatePurchaseSchema = purchaseSchema
  .partial()
  .omit({ userId: true })
  .required({ version: true })
  .strict();
```

しかし一覧・詳細・作成レスポンスの`purchase`には`version`が含まれず、Webの更新リクエストにも`version`がない。DBの更新条件は実装済みでも、クライアントが期待versionを送れないため、現状の画面フローでは使い切れていない。

### 4. 競合とNot FoundのHTTP表現が未整理

Repositoryは更新対象が0件の場合に`throw new Error('Failed to update purchase')`とする。Routeにはこの例外を409 Conflictや404 Not Foundへ変換する処理がないため、クライアントからは意味を区別できない500系エラーになる可能性がある。

### 5. テストが存在しない

ルートの`test`スクリプトは意図的に失敗する状態である。特に次は自動テストで確認する価値が高い。

- 同じPurchaseを同じ`version`で2回更新したとき、片方だけ成功すること
- 購入作成が同時に走っても在庫加算が失われないこと
- 購入食数の更新時にトリガーが在庫差分を正しく反映すること
- `batch`内の更新が0件の場合の扱い
- 購入削除と購入作成が競合した場合の在庫

### 6. 認可は未実装

DBには`user_id`があるが、APIは認証済みユーザーを扱わず、`GET /purchases`は全Purchaseを返す。`POST /purchases`の`userId`もリクエストbodyから受け取る。認証を追加する段階では、user IDはbodyではなく認証コンテキストから決め、すべての検索・更新・削除をそのIDで絞る必要がある。

## 学習の優先順位

1. APIを型チェック可能に戻し、削除経路を実行可能にする
2. Lost UpdateとAtomic Updateの違いを、購入作成・削除・在庫補正で比較する
3. `version`を読取レスポンスからPATCHリクエストまで通し、409 Conflictを返す
4. `batch`とトリガーの失敗時を含む統合テストを追加する
5. 認証とユーザー単位の認可を導入する

以降の資料は、この実装を具体例として同時更新と整合性を説明する。
