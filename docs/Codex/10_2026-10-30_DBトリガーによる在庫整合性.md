# 2026-10-30: DBトリガーによる在庫整合性

## なぜトリガーを導入したか

Purchaseの食数が変わると、MealStockも必ず変わる。このルールをServiceのJavaScriptだけに置くと、別のRoute、管理スクリプト、将来の直接SQLがPurchaseを変更したときに、在庫更新を忘れる危険がある。

そこで、Purchaseの変更を契機にDBが在庫を更新するトリガーが追加された。

## 更新トリガー

`0009_UpdateTrriger.sql`で導入され、`0010_UpdateTrriger_Re.sql`で再作成されたトリガーは、Purchase食数の差分を在庫に反映する。

```sql
AFTER UPDATE OF purchased_meal_count ON purchases
FOR EACH ROW
WHEN NEW.purchased_meal_count != OLD.purchased_meal_count
```

在庫へ反映する差分は次である。

```sql
NEW.purchased_meal_count - OLD.purchased_meal_count
```

たとえば食数を20から15へ変更した場合、在庫から5食を引く。金額だけの変更ではトリガーは起動しない。

## 削除トリガー

`0011_DeleteTrriger.sql`は、削除前の行を`OLD`として参照し、削除された食数を在庫から引く。

```sql
CREATE TRIGGER purchase_meal_count_delete
AFTER DELETE ON purchases
FOR EACH ROW
BEGIN
  SELECT RAISE(ABORT, '対応するデータが存在しません')
  WHERE NOT EXISTS (
    SELECT 1 FROM meal_stock WHERE user_id = OLD.user_id
  );

  UPDATE meal_stock
  SET current_meal_stock = ... - OLD.purchased_meal_count
  WHERE user_id = OLD.user_id;
END;
```

`RAISE(ABORT, ...)`により、対応するMealStockがない状態での削除はDBエラーになる。これにより「Purchaseだけ削除され、在庫が更新されない」状態を防ぐ。

## 作成・更新・削除の担当の違い

| Purchase操作 | MealStockを更新する仕組み | 使用する値 |
| --- | --- | --- |
| 作成 | Repositoryの原子的UPDATE式 | 今回の`purchasedMealCount` |
| 食数更新 | UPDATEトリガー | `NEW - OLD` の差分 |
| 削除 | DELETEトリガー | `OLD.purchased_meal_count` |

いずれも、更新直前のDBカラムを使い、在庫が負数にならないよう`MAX(0, ...)`を適用している。

## トリガー採用時の注意点

トリガーは整合性を強くできる一方、TypeScriptのRepositoryだけを読んでも在庫更新を追えなくなる。

また、作成時のSQL式、更新トリガー、削除トリガーには、「経過日数分を消費してから食数を加減する」という似たルールが3か所に存在する。将来、日付計算や下限のルールを変えるときは、すべての経路を同時に確認する必要がある。

## 必要な統合テスト

トリガーはmigration内のSQLなので、型チェックだけでは正しさを保証できない。少なくとも次をD1に対する統合テストで確認する。

1. 購入作成で在庫が仕入れ食数だけ増える
2. Purchase食数を減らすと、在庫も同じ差分だけ減る
3. Purchaseを削除すると、削除された食数だけ在庫が減る
4. 対応するMealStockがない場合、更新・削除が失敗する
5. 同日に複数操作しても、経過日数分の消費を二重計上しない

この日の変更は、在庫整合性を「Serviceが忘れないようにする」から「DBが破れないようにする」へ進めた変更である。
