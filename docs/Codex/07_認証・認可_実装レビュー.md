# MealCount の認証・認可

## この文書の対象

2026-11-20 時点で `origin/main` と一致しているコミット `01a4442` を読み、現在の実装を説明する。ここでいう認証は「誰であるかを確認すること」、認可は「その人が対象データを操作できるかを確認すること」である。

## 結論

認証は Better Auth による Cookie セッション、認可は **サーバーで確定した `session.user.id` を SQL の全ての対象条件に使う所有者チェック**で実装されている。購入と在庫について、クライアントが他人の `userId` を指定して読み書きする経路はない。

一方、ブラウザ側は未認証の 401 と、存在しない／他人のデータの 404 を個別に扱わず、現在は一律の失敗メッセージとしている。MVP として API のデータ保護は成立しているが、利用者への案内は今後の改善余地である。

## 全体の流れ

```text
React
  │ Better Auth client（Cookie を含めて送信）
  ▼
Better Auth の /api/auth/*
  │ サインアップ / サインイン / サインアウト / セッション取得
  ▼
ブラウザ Cookie
  │ credentials: 'include'
  ▼
Hono authMiddleware
  │ getSession(request headers)
  ├─ セッションなし → 401
  └─ session.user を Context に格納
                         │
                         ▼
              Purchase / MealStock の Route
                         │ user.id だけを Service へ渡す
                         ▼
                Repository の WHERE userId = session.user.id
```

この流れで重要なのは、`userId` をリクエスト JSON やパスから受け取らず、認証済みセッションからのみ得ている点である。

## 認証: セッションを作り、検証する部分

### Better Auth の設定

[`apps/api/src/lib/auth.ts`](/Users/inoueyuuji/mealcount/apps/api/src/lib/auth.ts:3) が Better Auth の生成元である。

- `emailAndPassword.enabled: true` によりメールアドレス・パスワード認証を有効化する。
- `database: env.meal_count_db` により、D1 の `user`、`session`、`account`、`verification` テーブルを利用する。
- `BETTER_AUTH_SECRET` をセッション関連の秘密値として使う。
- `trustedOrigins: ['http://localhost:5173']` と API 側 CORS の `credentials: true` により、ローカル Web アプリから Cookie を伴うクロスオリジン通信を許可する。

認証用テーブルは [`apps/api/src/db/schema.ts`](/Users/inoueyuuji/mealcount/apps/api/src/db/schema.ts:49) で定義されている。`session.userId` は `user.id` を参照し、`session.token` はユニークである。したがって、セッションとユーザーの結び付けは DB 上でも表現されている。

### 認証エンドポイント

[`apps/api/src/modules/auth/routes/userRoutes.ts`](/Users/inoueyuuji/mealcount/apps/api/src/modules/auth/routes/userRoutes.ts:7) は `/api/auth/*` の GET / POST を Better Auth 本体の handler に委譲する。アプリ自身がパスワード照合や Cookie 発行を再実装していない。

`/api/authorization/me` は同ファイルの middleware でセッションを検査し、成功時だけ Context に保存したユーザーを返す。ここは認証の動作確認用 API として読める。

### Web が Cookie を送る箇所

認証操作は [`apps/web/src/lib/auth-client.ts`](/Users/inoueyuuji/mealcount/apps/web/src/lib/auth-client.ts:3) の `createAuthClient` を通る。`fetchOptions.credentials: 'include'` があるため、ログイン後の Cookie を送受信できる。

通常 API 用の Hono RPC クライアントにも [`apps/web/src/lib/rpcClient.ts`](/Users/inoueyuuji/mealcount/apps/web/src/lib/rpcClient.ts:4) で同じ `credentials: 'include'` が設定されている。そのため購入 API への GET / POST / PATCH / DELETE にもセッション Cookie が載る。

## 認可: データの所有者をどう限定しているか

### 1. Route 共通の認証ゲート

[`apps/api/src/modules/auth/middleware/authMiddleware.ts`](/Users/inoueyuuji/mealcount/apps/api/src/modules/auth/middleware/authMiddleware.ts:4) は `getSession({ headers: c.req.raw.headers })` でリクエスト Cookie を検証する。

- `session?.user` がなければ `{ error: '未認証' }` と **401** を返し、次へ進めない。
- 成功時は `c.set('user', session.user)` で Hono Context に格納する。

購入ルートと在庫ルートは、それぞれ [`purchaseRoutes.ts`](/Users/inoueyuuji/mealcount/apps/api/src/modules/purchases/routes/purchaseRoutes.ts:12) と [`mealStockRoutes.ts`](/Users/inoueyuuji/mealcount/apps/api/src/modules/meal-stock/routes/mealStockRoutes.ts:8) で `.use(authMiddleware)` を先頭に持つ。従って、各 Route が `c.get('user').id` を安全に利用できる。

### 2. Purchase の行レベル認可

Route は `const userId = c.get('user').id` を取り出して Service に渡す。Repository 側では次のように、ID 条件と所有者条件を常に組み合わせている。

| 操作 | Repository の条件 | 意味 |
| --- | --- | --- |
| 一覧 | `purchases.userId = userId` | 自分の購入だけを返す |
| 1件取得 | `id = ? AND userId = ?` | 他人の ID では取得できない |
| 更新 | `id = ? AND version = ? AND userId = ?` | 所有者かつ最新 version の行だけ更新できる |
| 削除 | `id = ? AND version = ? AND userId = ?` | 所有者かつ最新 version の行だけ削除できる |

実装箇所は [`apps/api/src/modules/purchases/repositories/purchaseRepository.ts`](/Users/inoueyuuji/mealcount/apps/api/src/modules/purchases/repositories/purchaseRepository.ts:75) からである。作成時も [`buildCreateQuery`](/Users/inoueyuuji/mealcount/apps/api/src/modules/purchases/repositories/purchaseRepository.ts:57) は Route から渡された `userId` を保存する。作成リクエストに `userId` フィールドはないため、別ユーザーになりすます入力口がない。

他人の Purchase ID を指定した場合は、所有者条件を満たさず取得できない。現在の API は「存在しない」と「他人の所有物」を同じ **404** にする。これは、リソースの存在自体を推測させにくい設計である。

### 3. MealStock の行レベル認可

[`apps/api/src/modules/meal-stock/repositories/mealStockRepository.ts`](/Users/inoueyuuji/mealcount/apps/api/src/modules/meal-stock/repositories/mealStockRepository.ts:15) も同様である。

- 取得は `id` と `userId` の両方で絞る。
- 手動補正の更新は `id`、`version`、`userId` の全てを WHERE 条件にする。
- ユーザーごとに在庫を1件にする `mealStock.userId.unique()` も [`schema.ts`](/Users/inoueyuuji/mealcount/apps/api/src/db/schema.ts:38) で設定されている。

購入作成に伴う在庫更新も `buildAddPurchaseMealCountQuery` が `id` と `userId` を条件に含めるため、購入処理から別ユーザーの在庫を更新することはない。

## 認証と認可を分けて読むポイント

`authMiddleware` は「リクエストに有効なセッションがあるか」を判定するため **認証** である。一方、Repository の `WHERE ... userId = session.user.id` は「そのユーザーがその行を操作してよいか」を判定するため **認可** である。

この二層が必要になる理由は、ログイン済みであっても任意の `/:id` を指定できるからである。認証だけでは IDOR（他人の連番 ID を指定して操作する問題）を防げない。現在の実装は、所有者条件を DB 更新・削除の SQL にまで含めているため、Route だけの条件分岐より強い。

## 現時点の評価と注意点

### MVP として満たしている点

- Cookie セッションを API で検証している。
- 保護対象の Purchase / MealStock 全 Route に認証 middleware を適用している。
- クライアント入力ではなくセッション由来の ID を所有者判定に使っている。
- 取得、更新、削除の DB 条件にも所有者 ID を含めている。
- 楽観的ロックの `version` と所有者条件を同じ更新条件に入れている。

### 現在の境界と、今後確認したい点

- `trustedOrigins` と CORS の origin はローカル開発用の固定値である。本番公開時は本番 Web の origin と API URL を環境ごとに設定する必要がある。
- 権限ロール（admin など）は未実装である。ただし現仕様は「自分のデータだけを扱う」MVP のため、ロール認可がないこと自体は不足ではない。
- API の 401 / 404 / 409 は Web 側で個別に判別されず、各 API 関数が一般的な `Error` に置き換える。認証の保護機構には影響しないが、ログイン画面へ誘導するなどの UX はまだない。
- `authMiddleware` と `/api/authorization/*` の middleware は、同じセッション検証を別々に記述している。現状は機能するが、認証エラー本文が `未認証` と `Unauthorized` で異なる。共通化は将来の保守上の検討点である。
