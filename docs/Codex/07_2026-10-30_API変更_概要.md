# 2026-10-30 API変更の概要

## 対象範囲

この資料は、2026年10月30日の次の6コミットに含まれるAPI変更を対象にする。

```text
4d473dd → 5657e33 → 32e90e4 → 3725418 → a3efc27 → 099ec2f
```

2026年10月31日の`version = 0`判定の修正は対象外である。

## この日に実現したこと

購入と在庫の同時更新を、Serviceが読み取った古い在庫値を保存する方式から、DBの現在値・DBトリガーを使う方式へ移行した。

```text
購入作成
  Purchase INSERT
  + MealStock の原子的加算

購入食数の更新
  Purchase UPDATE（versionで競合検出）
  + UPDATE triggerによる在庫差分更新

購入削除
  Purchase DELETE（versionで競合検出）
  + DELETE triggerによる在庫差分更新
```

## 変更の対応表

| トピック | 主な実装箇所 | 意図 |
| --- | --- | --- |
| 楽観的ロック | `db/schema.ts`、`purchaseRepository.ts` | 古い編集・削除による上書きを防ぐ |

| DELETEの競合検出 | Route / Schema / Repository | versionをqueryで受け、古い削除を拒否する |

## 設計上の変化

変更前は、Serviceが次のように処理していた。

```text
MealStockをSELECT
→ JavaScriptで在庫を計算
→ PurchaseとMealStockを更新
```

この方式では、SELECTとUPDATEの間に別リクエストが入ると、先行リクエストの在庫更新を後続リクエストが上書きする可能性がある。

変更後は、操作ごとにDB側へ整合性の責務を寄せている。

```text
作成: UPDATE式の右辺でDBカラムを参照する
更新: DB triggerが旧値と新値の差分を使う
削除: DB triggerが削除前行（OLD）の食数を使う
```

これは、MealCountにおける在庫を「Purchaseの変更に追随する派生データ」として扱う設計である。

## 評価

この日の変更は、単純なCRUDから、競合と整合性を意識したAPIへ進む重要な改善である。

特に良い点は、在庫更新のルールをRouteやServiceに散らさず、原子的UPDATEとトリガーへ集約し始めた点である。一方、トリガーは通常のTypeScriptコードから見えないため、migrationのレビューと統合テストが必須になる。
